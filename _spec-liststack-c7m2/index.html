List Stacking + Matching

Mini-spec (approve the shape before I code) · Priority #1 · 2026-08-23

What we're building: the ability to pull several lead lists together, collapse duplicates so each real property appears once, and score every property by how many lists it lands on — so the hottest, most-motivated sellers float to the top automatically. Two features, one build, because stacking can't work until matching does.

1. The user experience

A new Lists area on the desktop command center:
  • Pick 2+ lists to stack (checkboxes): Foreclosure, Probate, Tax-delinquent, + any CSV you import
  • The grid rebuilds with a Stack Score column = # of lists that property is on
  • Each row shows source badges so you see WHY it's hot at a glance
  • Sort by Stack Score (default), filter "show me 2+ / 3+ lists" = your morning call pile

2. Under the hood — matching (the hard part)

Stacking is trivial once we can say "these two rows are the same house." That's matching. Plan:

Canonical property key

  • Strongest: APN + county + state — the legal parcel id. When present, this is the match key (ties into the APN dedup work already started).
  • Fallback: normalized street + zip — lowercase, strip punctuation, standardize suffixes (St/Street, Ave/Avenue), fold unit/apt, expand directionals (N/North).
  • Each incoming row resolves to a canonical property row (new properties table, or a canonical_key column on existing rows). One property = one map pin (kills the dup problem).

List membership

  • A list_membership table: (property_id, list_type, source, added_at).
  • Stack Score = count of DISTINCT list_type per property. Cheap to compute, indexable.
