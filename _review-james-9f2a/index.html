What it does (context)

At its core OffRamp REI is a data aggregator built specifically around pre-auction, high-equity foreclosures. It pulls that inventory nationally, fuses distress data that no single source joins (county recorders, PACER bankruptcies, probate, liens, MLS, skip-trace) into one scored lead record, and runs an AI agent on top that enriches and works the phone.

Secondary use case — the buyer side. By scraping recorded deeds from completed auction/trustee sales, we identify who is actually buying at auction (repeat cash buyers, funds, flippers) and build a live cash-buyer list from public record. Same pipeline, opposite end of the deal: the primary side finds the distressed seller before the sale, the secondary side finds the proven cash buyer after it. Product walkthrough: offramprei.com/how-it-works.

The USP: nobody else holds the entire lifecycle of a single property in one record — pre-auction distress → the foreclosure/auction event → the auction result (did it sell, for how much) → who bought it, plus enriched data on that buyer. Every incumbent has a slice; we chain the whole timeline, seller side through buyer side, on the same parcel.

Current stack & scale today

  • Data / DB: Supabase (Postgres) — the hit_list is the foreclosure universe (~6,700 live leads); crm.contacts is the CRM (~33k rows). Sorts/filters on equity, auction date, state/county, pipeline.
  • App: Expo / React-Native (web + mobile), mobile is the source of truth; Google Maps layer with 2,000+ pins.
  • External data APIs: REAPI + DealMachine (property/deeds/enrichment/photos), Tracerfy/DealMachine (skip-trace), Twilio (voice/SMS), plus per-county recorder + auction/listing scrapes.
  • Orchestration: cortextOS — an autonomous-agent engine (agents + cron + message bus) already runs ingestion/enrichment/QA jobs on a schedule; a daily leads-QA loop runs today.
  • Users today: ~6 partner tenants, heading toward paid multi-tenant.

Where I'm looking for your take

HURDLE 1

Scalability & API-call limits on the data layer

The engine scales fine — the bottleneck is data. Right now I'm leaning on enrichment/property APIs (REAPI, DealMachine, skip-trace) plus per-county scrapes. At real volume that means a lot of API calls, rising cost-per-lead, rate limits, and the risk a vendor cuts us off. Foreclosure data is scattered across ~3,100 counties, each in a different format/cadence — so "cover the US" isn't one integration, it's thousands.

The honest trajectory: scraping (county portals, foreclosure.com, auction.com) is how I bootstrap the MVP cheaply today, but I don't think it survives to production — it's brittle, and scraping commercial sites like foreclosure.com / auction.com raises copyright / terms-of-use exposure and won't be reliable at scale. So production coverage has to move onto licensed enterprise APIs and public-record data. The one place scraping likely does stay legitimate long-term is foreclosing / closing-attorney (trustee) websites that actively publish auction notices as public notice — that content is meant to be public, so it's the durable scrape surface. Enrichment (REAPI, PACER) stays on-demand so the expensive calls scale with the funnel, not the raw universe. (Skip-trace / contact enrichment I run separately for our own outreach — out of scope for this scalability question.)

My current thinking: keep a thin national index from an enterprise vendor for the 50-state floor, then hydrate deep on-demand — only pull expensive county-level detail for a record when it actually enters the funnel, and cache it. Buy the breadth, build the freshness edge on top, and wrap everything behind one internal normalization API so I can swap a vendor without touching the app.

Questions for you: Is on-demand hydration the right call vs. bulk ingest? What enterprise data API would you anchor national coverage on? How do I keep API cost-per-lead sane at volume — caching, tiering, batching? And how do I not build a business that dies if one vendor changes terms?
HURDLE 2

Moving this from my internal system to a real app platform

Today it runs as my own back-office desk. To let the 6 partners (and eventually paying subscribers) use it, I need to turn it into a proper multi-tenant app — fast enough to serve a sortable 6,700-lead list + a live map + per-property enrichment to a phone without freezing the device or blowing the data bill.

Architecture I'm considering: split write-heavy scraping/enrichment (staging → normalize → upsert into serving tables) from reads so the app never waits on a scraper; idempotent upserts on APN + county FIPS for dedup; composite indexes for the equity/auction-date/state sorts; PostGIS + server-side clustering so the map ships pins by viewport, not all at once; cursor pagination; a materialized "worth-a-call" scored list; Expo/React-Native web (mobile as source of truth); row-level security for multi-tenant with per-tenant metered API caps.

Questions for you: Is that the right shape for a first real platform, or am I over/under-building? What would you prioritize to get partners on it soonest? Build vs. buy on the app layer? And where do multi-tenant + metered usage-caps most commonly go wrong?
HURDLE 3

Getting it to production-grade — and QA for an app that runs data services

Standard app QA tests the code. My harder problem is that the data itself can be wrong even when every test passes — a county drops a lien, a feed goes stale, an equity number is off by a mortgage, a scraper silently returns half the fields. If bad data reaches a user, they call the wrong lead or, worse, buy on fake equity. So "production-grade" here means the pipeline has to be trustworthy, monitored, and self-healing, not just the UI.

What I have / am considering: a QA/validator agent that sanity-checks every pull (missing fields, dropped liens, implausible equity) and flags/retries; self-healing scrapers that detect a county form change, retry, and escalate; idempotent upserts that double as a change-log; and a daily leads-QA loop that already runs today. What I don't have is a real production discipline around it — SLAs, monitoring/alerting, data-freshness guarantees, staging-vs-prod, incident response.

Questions for you: How do you QA data correctness (not just code) at scale — golden datasets, statistical drift checks, source cross-validation? What does a real monitoring/alerting stack look like for a data pipeline like this? What's the minimum bar to honestly call this "production-grade" for paying users, and what would you not ship without?

Why the problem is technically hard (context for the three above)

  • The data is fragmented by design — no national land database; property is recorded county-by-county, each with its own portal, format, and cadence, many semi-manual. "Cover the US" is thousands of integrations, not one.
  • The fusion is the hard part, not the scrape — joining foreclosure + bankruptcy + probate + equity into one record that's actually correct is the real engineering. A single stale or conflicting source silently corrupts the join.
  • Real-time delivery at scale — serving a large, freshly-enriched, sortable dataset fast to a phone (map + list + per-property detail) without blowing the data bill is its own systems problem.

The honest constraints

  • Unit economics at scale — I need a defensible data-cost-per-lead and per-state number before I push volume.
  • Vendor dependency — need multi-source redundancy so no single cutoff is fatal.
  • Compliance — skip-trace is DPPA/GLBA-gated; that has to be clean.
  • Focus — I'm rebuilding the core business at the same time, so I need the highest-leverage moves first, not a two-year rebuild.
